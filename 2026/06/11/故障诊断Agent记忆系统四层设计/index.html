给故障诊断 Agent 装上记忆系统：四层记忆模块设计实践

发表于 2026-06-11 分类于 AI Agent 阅读次数： 本文字数： 1.5k 阅读时长 ≈ 6 分钟

背景

做故障诊断 Agent 时遇到一个核心问题：Agent 没有记忆。

用户报一个 K8s Pod CrashLoopBackOff，Agent 每次都要走一遍完整诊断流程：describe pod → 看 logs → 查 events → 定位根因。第二次遇到同样的 OOM 问题，还是走同样的流程。

这就像厨师每次炒菜都要重新看一遍菜谱——效率低，也不智能。

更进一步，不同用户的环境不一样：

  • 用户 A 的集群用 Calico v3.27，网络问题频发
  • 用户 B 的集群用 Flannel，从来没出过网络问题

如果所有用户的经验混在一起，Agent 的决策会被噪音干扰。

目标

设计一套记忆系统，让 Agent 能：

  1. 记住高频故障 — 见过的病，下次直接开药
  2. 区分共享知识 vs 用户私有知识 — 不让 A 的历史干扰 B 的诊断
  3. 自动沉淀经验 — 诊断完自动学习，而不是等人来写文档
  4. 老知识自动过期 — 集群版本升级了，过时的 SOP 自动标记

关键区分点

面试时被问得最多的是：SOP 和 Reference 到底有什么区别？

共享 vs 隔离

这里有一个容易被忽视的设计决策：Agent 实例是共享的，但记忆按用户隔离。

为什么共享 Agent 实例？因为诊断逻辑对所有人都一样，没必要每人起一个实例。但记忆不能混——A 团队的历史故障 B 团队不需要知道。

存储方案

SOP_INDEX.md 常驻 system prompt（几百 token），Agent 启动时就知道”有哪些 SOP 可用”。正文按需加载，每次 top-5。

过期机制

纯靠时间判断不靠谱。判断 SOP 是否过期的标准不是”过了多久”，而是**”SOP 假设的环境状态是否仍然成立”**：

  1. 时间维度：创建超 30 天未验证的标记为 stale
  2. 事件驱动：集群版本升级时主动标记相关 SOP
  3. 使用反馈：连续 3 次被标记”无效”自动过期

Agent 执行过期 SOP 前，先用 MCP 工具验证关键前提——“该 SOP 依赖的 Ansible 版本是否还是当前版本？”

总结

层级 类型 作用域 本质 来源
SOP project 共享 怎么查（流程） 人工维护
Reference reference 共享 是什么（结论） 自动沉淀
User user 用户隔离 环境配置 自动记录
Feedback feedback 用户隔离 诊断偏好 自动学习

这套设计的核心思想：共享诊断能力，隔离用户上下文。

SOP 告诉 Agent 怎么排查问题，Reference 告诉 Agent 这个问题以前修过，User 告诉 Agent 这个用户的环境是什么，Feedback 告诉 Agent 这个用户喜欢怎么查。

四层配合，Agent 就能像一位经验丰富的运维工程师一样——见过的病直接开药，没见过按流程查，查完自动记笔记。
