生产级 Agent 流式输出：从任务解耦到断线续看

发表于 2026-11-08 分类于 AI Agent 阅读次数： 本文字数： 11k 阅读时长 ≈ 40 分钟
Agent 的流式输出有它自己的形状——任务比请求长、事件密度极高、中间有长静默期、还有明确终态。本文先讲清任务与连接为什么要拆开，再依次处理事件分层、静默期保活、半开连接的判定、序号补发与快照重建、客户端自救、配额与背压、多实例与发布，并给出可运行的 FastAPI 与 TypeScript 实现。

生产级 Agent 流式输出：从任务解耦到断线续看

10:32，任务已经在数据库里完成；10:50，页面还显示”生成中”。刷新一下，答案立刻出现。

这个场景里没有一行代码写错。任务跑完了，数据也落了库，四条长连接各自工作正常——问题出在一个没人明确定义的地方：**谁负责发现”这条连接已经没用了”**。

Agent 的流式输出和普通消息推送不是一回事。普通推送是”服务端有消息就发”，而 Agent 是”任务比请求长得多，中途可能完全安静，最后还有明确的成败”。这三点决定了它不能用”一个请求跑到结束”的模型，也不能只靠一条连接活着。

下面按一条连接的生命周期展开：先讲为什么必须把任务和连接拆开（第 1 节），再讲协议选型和客户端选择（第 2 节），然后是事件模型（第 3 节）、静默期保活与半开连接（第 4 节）、序号与快照恢复（第 5 节）、客户端自救（第 6 节），最后是资源治理、多实例、发布和可观测性。后端 FastAPI 实现和前端 TypeScript 客户端都可运行。

0. 结论

如果只记六句：

  1. 任务不能挂在连接上。POST 创建 Run，后台跑；GET stream 只是订阅窗口。刷新、断网、换设备只是”窗口没了”，不是”任务没了”。
  2. 事件要分两类。token 增量每秒几十条、丢了能重建，不该占号进补发日志；步骤、工具调用、终态必须有序号、必须能补。混在一起，日志会被 token 撑爆。
  3. 心跳只防代理掐断，不证明连接活着。心跳也是字节，同样会卡在发送缓冲区里。能发现”对面已经没了”的是客户端读超时。
  4. 序号不连续就停，不要在缺口上继续叠事件。缺一条就可能错一整段。
  5. 恢复靠三块积木：序号发现缺口、补发填平缺口、快照在补不齐时重建。
  6. 终态先落库，再宣布。顺序反了就会出现”页面显示完成、数据库还在 running”的假成功。

1. 先把任务和连接拆开

1.1 挂在响应上的三个问题

最直觉的做法是把 Agent 执行直接挂在 HTTP 响应上：一个请求进来，服务端开始跑，跑到哪写到哪，响应结束任务结束。

本地能跑，上线会遇到三类问题。

代理有读超时。 Nginx 默认 proxy_read_timeout 60 秒，而一次工具调用可能就超过 60 秒。代理先断，断开之后任务是否继续取决于框架有没有在客户端断开时取消协程——可能留下孤儿任务，也可能把任务取消掉。行为不确定，这本身就是问题。
浏览器刷新就是断开。 用户按 F5，TCP 连接没了。如果任务和响应绑定，这次执行跟着作废。一个跑 15 分钟的研究任务，用户刷新一次全白跑。
执行上下文被标签页绑定。 每个标签页各自发起一次执行，执行上下文数等于标签页数；同一会话重复发送还会产生重复执行。
这三条合起来是一个更糟的后果：用户以为任务丢了，会重复发送；重复发送触发 409、排队，甚至重复执行。一个连接问题最后会变成业务问题。

1.2 Run 与订阅窗口

把两件事拆开：

  • POST /api/agent/runs 只负责创建 Run——把用户消息、queued 状态的记录写进数据库，立刻返回 run_id。
  • 真正的执行由后台 producer 负责，和 HTTP 请求无关。
  • GET /api/agent/runs/{id}/stream 只是订阅窗口，打开、关闭、刷新都不影响 Run。

流式端点不持有任务，只负责把事件读出来写给客户端。它被取消、被关闭、被刷新，都不影响 execute_run：

replay_then_live 把三件事串起来：补日志、进实时、终态收尾。

到终态就主动关流，客户端能区分”正常结束”和”半路 EOF”。

1.3 拆开之后换来了什么

维度 挂在响应上 拆成 Run
刷新页面 任务中断 任务继续
代理超时 连接断，任务状态不明 只影响观察窗口
多标签 每个标签一条执行上下文 一个 Run，多个订阅
断线恢复 无法恢复 序号补发 + 快照
换设备 无法继续 换个窗口继续看

代价是要额外维护 Run 存储、执行者、恢复协议。这是后面所有复杂度的来源，也是这套架构真正的成本。 如果任务只跑几秒、用户也不会刷新，那这条路是过度设计。

2. 选型：SSE 的甜点区

2.1 为什么不直接轮询

轮询的问题是延迟和成本二选一：1 秒一次，10 分钟任务每个客户端 600 次请求；5 秒一次，用户感知的延迟就是 5 秒。

轮询也不是一无是处——它没有半开连接问题，每次请求都是独立的。所以常见组合是：状态查询用轮询，实时增量用 SSE。Noesis 的信令流就是这个思路：信令只推”有任务启动”的提示，丢了靠主动查询自愈。

2.2 连接配额会先撞墙

选 SSE 之前先算连接数。浏览器对同源 HTTP/1.1 的并发上限通常是 6。

算的时候要把同页所有常驻流都算上，不只是 run 流。比如一个聊天页可能还有任务目录流、通知流；跑任务时再加一条 run 流，一个标签页就是 2~3 条。两个标签页接近 5 条，普通请求只剩一两个名额——这时页面不是”推送慢”，是接口排队。

两个解法：生产入口开 HTTP/2，多路复用后所有流共用一条连接；或者把常驻流放到独立子域、独立连接池。

WebSocket 升级后走独立配额（Chrome 每主机 255 条、Firefox 默认 200 条），不占 HTTP/1.1 每源 6 个名额——只有握手是一次 HTTP/1.1 请求。所以它确实能绕开这个限制。仍然选 SSE 是工程取舍：不引入第二套传输和鉴权，常驻流也不多。

场景 更合适 代价
服务端单向推送，已有 HTTP 鉴权、代理、日志 SSE HTTP/1.1 下每条流占一个连接
双向低延迟，客户端持续上行 WebSocket 独立配额，但多一套传输和鉴权
跨标签页广播 一个服务端连接 + BroadcastChannel 同源分发 只能同浏览器同源
任务秒级结束，可接受轮询 普通 HTTP + 轮询 延迟和请求数二选一

SSE 的甜点区是”任务比请求长、上行很少、基础设施已经是 HTTP”。超出这个区间，它的优势会迅速变成约束。

2.3 EventSource 为什么不够用

EventSource 帮你做了三件事：解析 event: / data: 帧、断线自动重连、把 id: 回填成 Last-Event-ID 请求头。

但它有两个硬限制，恰好卡住 Agent 的 run 流。

不能设置自定义请求头。 new EventSource(url) 只接受 URL，鉴权只能靠 Cookie。如果鉴权是 Bearer token，它做不到——只能把 token 拼进 URL，而 URL 会进 access log、浏览器历史和 Referer。
重连行为不可控。 URL 在构造时固定，浏览器自动重连时不会按最新的 sequence 改写 after_sequence；也不能在跳号时主动中断、先拉快照再重连。

还有一点容易被忘掉：EventSource 内部管理 read()，你拿不到读超时。而读超时是发现半开连接的唯一可靠手段（第 4.3 节）。
所以 run 内容流用 fetch + ReadableStream + 自己写的解析器。任务目录流仍然可以用 EventSource，因为它不需要这些控制。

用 fetch 之后鉴权也回归普通做法，token 走请求头，不用再进 URL：

如果项目里必须用 EventSource（老浏览器、既有代码不好改），才需要一次性凭证：先用正常请求换一个 30 秒有效、只能用一次的随机串，再拼进 URL，用掉即销毁。代价是每次重连多发一个请求，而且浏览器自动重连不会带新 token，等于又得自己接管重连。

2.4 自己解析帧的代价

看起来简单，坑不少：data: 可以多行，要按行拼接；注释帧要忽略；一个 TCP 包可能只包含半帧，不能假设每次 read() 都拿到完整事件；[DONE] 是纯文本，不是 JSON。

自己实现解析和重连，换来的是控制权：能带鉴权头、能带 after_sequence、能在跳号时停、能按代际丢弃过期连接。代价是解析器的正确性要自己保证——SSE 的线格式只有几行规范，但边界条件足够让一个粗糙的解析器在弱网下出错。

3. 事件模型：哪些事件占号

3.1 一帧长什么样

一帧由 event:、data: 和空行组成。协议还定义了 id: 和 retry:，这里都没用：序号放在 data 里，重连参数走 query。因为这两件事都需要业务层控制，交给浏览器反而拿不回来。

这个选择是有代价的：放弃了浏览器自动补发的能力。换回来的是”重连几次、从哪个序号开始、什么时候放弃”全部由业务代码决定——而自动补发只覆盖”缓存内”这一种恢复，超出缓存要切快照、跳号要停、慢订阅者要隔离，这些都在协议之外。

3.2 durable 与 transient

一次两千字的回答会产生两千条 token 增量。如果每条都占号，一次对话写几千条日志，补发时前端要重放几千帧——本来可以直接给一段完整文本的操作，变成慢速回放。

两类事件的性质不同：

  • transient：text-delta、thinking-delta。价值在”字在往外冒”的实时体感；用户稍后回来只关心”这段话是什么”。
  • durable：run-started、step-started、tool-call、tool-result、assistant-message、run-finished、error。是”发生了什么”的记录，几分钟后回来还需要知道。

3.3 摘要锚点：让增量可以丢

assistant-message 是整套设计的关键：每完成一步，服务端把该步的完整文本作为一个 durable 事件发一次。

这样即使所有 delta 都丢了，客户端拿到这一条就能补齐整段话，而且比逐个重放 delta 快得多。
代价是前端要处理”先看到 delta 拼出的文本，又收到 assistant-message 覆盖它”。规则是：以 assistant-message 为准，同一步的 delta 之后忽略。

3.4 序号来源与保留窗口

序号必须单调递增、按 run 隔离。单实例用内存计数器；多实例用 Redis 的 INCR，原子操作不会撞号。

保留窗口指每个 run 保留最近多少个 durable 事件，用于补发。一次运行通常只产生几十条（每步 2 条、每个工具 2 条、加开始和终态），2000 条能覆盖很长的续看窗口，占用也就几百 KB。超出窗口靠 resync 全量重建。

4. 保活与掉线判定

4.1 静默期为什么会被掐断

有用户反馈：”只要 agent 开始调工具，过一会儿就断开，然后重新连上，工具结果就没了。”
日志里有一个非常规整的规律：断开的间隔是整整 60 秒。

Nginx 的 proxy_read_timeout 默认 60 秒，含义是”上游 60 秒没吐出任何字节就掐断”。而 Agent 在模型思考、工具执行时完全安静，完美符合掐断条件。这不是偶发故障，是必然发生的。
断开的间隔精确等于代理配置，这个规律本身就是最好的诊断线索：看到”整分钟断”，先查代理，别查代码。

4.2 keepalive 的实现

心跳的作用不是”给客户端发信号”，是让代理看到连接上还有字节。客户端根本不处理它。
实现上不另起定时任务，而是把”等下一个事件”加上超时：等到了就发事件，等不到就发一个注释帧。

": keepalive\n\n" 是注释帧，以冒号开头，规范规定客户端必须忽略，作用只有”让连接上有字节流动”。mark_written() 不产生流量，只更新一个内存时间戳——它只用于指标和排障，不承担回收职责（回收靠第 7.3 节的 send 写超时）。

4.3 半开连接：心跳救不了你

有一种故障，keepalive 完全帮不上忙。
用户把笔记本从 Wi-Fi 切到手机热点。TCP 连接进入”半开”状态：客户端和服务端都以为连接还在，实际上中间的路由已经不通了。

半开连接的特点是：写不会立刻报错，读会一直等。

服务端往 socket 写，内核先把数据放进发送缓冲区，write 立刻返回成功；数据能不能到对端，要等 TCP 重传和超时才知道。客户端这边，reader.read() 等的是一个永远不会来的字节。
所以”对方还在发心跳就说明连接活着”这个推断不成立——心跳也是字节，也会卡在同一个缓冲区里。心跳像敲门，只能证明你想进，不能证明屋里有人。
TCP 自带的 SO_KEEPALIVE 也指望不上：默认探测间隔通常两小时，而且只探连接是否可达，不保证应用层还能处理数据。对一个 15 分钟的任务来说，等它发现，任务早跑完了。

真正能发现掉线的是客户端的读超时：超过 45 秒没收到任何字节（包括 keepalive），就判定这条连接不可用，主动取消并重连。

拿到 "timeout" 就取消 reader、进入恢复流程。EventSource 拿不到 read()，所以做不了这件事——这是第 2.3 节选 fetch 的根本原因。

4.4 两个数字必须成对

服务端 keepalive 15 秒，客户端读超时 45 秒。
心跳间隔必须明显小于读超时，否则网络只是抖一下，客户端就误判成断线，反复重连。把 keepalive 改成 60 秒、读超时仍是 45 秒，客户端会在每次心跳之前就先超时，日志里满屏 reconnect。

反过来，读超时设成 0（等于不设），就会出现开头那个场景：任务 10:32 完成，页面 10:50 还显示生成中，read() 挂了 24 分钟。
这两个实验说明：keepalive 和读超时是一对参数，不能单独调。 45 秒是折中——再短会误杀弱网，再长会让恢复变慢。

4.5 传输链路：缓冲必须关掉

心跳解决了”被掐断”，紧接着会遇到另一个问题：连接好好的，但文字是一段一段蹦出来的。
两处会攒数据。代理默认 proxy_buffering on，先把上游响应攒在缓冲区再给客户端，20 毫秒一个 delta 到了浏览器变成 2 秒一批。应用层 gzip 同理，text/event-stream 也在压缩范围内。
判断方法：服务端日志的时间戳密集、客户端收包稀疏，问题在中间链路；服务端本身就是一批一批写的，问题在生成器。

5. 恢复：序号、补发、快照

5.1 补发为什么必须连续

客户端带着 after_sequence=38 重连，服务端从 39 开始补。
补发必须是连续的，中间不能跳号。前端拿到 39、40、42 三帧，如果继续应用，界面就处于”看起来正常但实际错位”的状态——可能少了一条工具调用，也可能少了终态。所以正确反应是停下当前连接，重新对齐。
服务端这一侧的判断：

游标落在保留窗口之外时不能静默跳过，否则客户端会安静地显示一个残缺的会话。

还有一个反向边界同样要处理：游标大于服务端最新序号。它不常见，但出现时会静默卡死——比如客户端把别的 run 的游标带了过来，或者服务端重建过事件日志。此时服务端没有”未来的事件”可以补，客户端又会把后续每个正常事件都判成”序号 <= 游标”而当作重复丢掉，两边一起等，界面永远不动。这种情况也要发 resync，让客户端以快照的序号重新对齐。

5.2 快照：补不齐就重建

序号和补发只覆盖”缓存内”的断线。断得久了、窗口裁掉了，就只能重建——拉一份权威快照，把当前状态整个给客户端。
快照和补发不能互相替代：

  • 只给快照：用户不知道中间调了什么工具、失败过没有。
  • 只补日志：用户要等所有事件重放完才能看到完整内容。

所以顺序是：先快照，再补增量，最后进实时。

5.3 快照必须含正在生成的那一段

快照不带 sequence，它由端点补上——RunState 不该知道事件日志的存在，那层依赖反了会让快照函数变得难测。

partial_text 是最容易漏的字段。只按”步骤完成时才有完整文本”设计快照，会漏掉一个高频场景：一次回答几十秒，用户在这一步中间刷新。此时 assistant-message 还没产生，快照里这一步是空的，而后续 delta 只包含”从刷新那一刻往后”的内容——前半段永久丢失。

所以生成器每收到一个 delta 就顺手更新缓冲区：

partial_text += delta 在大文本下是 O(n²)。一次回答几千字可以接受；几十万字就换成列表加长度记录，快照时再 join。

5.4 快照之后序号怎么接

快照里带 sequence，客户端把本地游标直接设成它，然后从这个号之后继续补。这样”快照 + 补发”能无缝衔接：

有一个容易漏的点：**[DONE] 不等于成功**。SSE 流结束时服务端会发一个 data: [DONE]，它是传输层哨兵，不是业务终态。

terminalObserved 只在真的收到 run-finished（或快照是终态）后才置位。少了这个判断，就会出现”界面显示完成，但数据库里还在 running”的假成功。

EOF 是传输事实，终态是业务事实。

6.3 一次重连的七步

  1. 发现异常：read() 超过 45 秒没返回，或者序号不等于 cursor + 1。
  2. 取消当前连接：reader.cancel()，避免旧连接继续往同一个状态机里写。
  3. 拉权威快照：把 snapshot 交给同一个分派函数，游标设成它的 sequence。
  4. 判断是否还要继续：用户可能已经切走、点了停止，或者已经是终态；不 active 就安静退出。
  5. 退避：500 * 2^attempt 毫秒，封顶 8 秒，加 0~250 毫秒抖动。
  6. 重新订阅：带当前游标。
  7. 恢复接收：服务端决定补发还是快照，客户端继续按 cursor + 1 校验。

上面每一步都要先问一句”这条流还有效吗”。用户切换会话或点停止的一瞬间，旧连接的 read() 可能还挂着，几百毫秒后它突然返回一批事件——如果直接应用，就会把上一个会话的内容写进新页面。

6.5 幂等

补发和重连天然产生重复：客户端收到事件但还没来得及更新游标就断了，重连后这条会再来一次。去重不能只按序号（那是传输层），要按业务主键——比如”哪个 run 的哪个 step 的哪个工具调用”。

7. 资源治理：配额、背压、回收

7.1 配额与 6 连接限制

服务端要限额，替浏览器兜底：

3 条是替浏览器兜底：一个标签页通常 2 条流，留一点余量给普通请求。5000 条取决于部署机器——每条占一个 fd、几十 KB 缓冲，ulimit -n 要大于连接数加上其他 fd。这个数不能抄。

配额按连接算，不按 run 算。同一个 run 开两个标签页就是两条连接、两个独立游标：服务端把事件广播给两条连接，各自从自己的序号接。所以单用户上限必须覆盖”标签页数 × 每页流数”，否则用户一多开就被自己的配额挡住。反过来说，如果只是同浏览器里多开标签，可以用一个连接 + BroadcastChannel 分发，把 6 个名额的消耗压到 1 条。

7.2 背压：断连接，不丢事件

用户反馈过”回答中间少了一段工具调用”，刷新后又正常了。查下来不是补发错，是那几秒连接队列满，事件被直接扔掉了。
队列满时有两种处理：丢事件，或者断开连接。
丢事件的后果是用户看到一个静默缺口，而且没有任何机制能发现它。断开的后果是短暂的重连提示，内容能靠游标补回来。

绝不 await queue.put：那会让一个慢客户端反向阻塞发布方，而发布方通常是唯一的循环，等于一条慢连接拖死所有人。

7.3 回收半开连接：时间戳扫描不够，要给 send 加超时

第 4.3 节说过，发现掉线的责任在客户端读超时。服务端这边能做的只是兜底回收——客户端进程被杀、笔记本合盖之后不会重连，配额得有人放开。

很多实现的第一反应是”记一个最后写时间，定期扫描清理”：

这套机制单独用是无效的，这是踩过才明白的一点。半开连接上真正的阻塞点不是”写很慢”，而是 yield 卡在 ASGI 的 send 里：生成器被挂起在那一行，永远轮不到下一轮循环去检查 closing 标记。扫描任务可以把它从注册表里删掉，但生成器本身还活着、还占着任务和连接——标记只是自欺欺人。

真正有效的手段是给每一帧的 send 加超时，让阻塞的那一行自己抛错，把生成器从挂起状态里拽出来：

超时值取 180 秒是”远大于 keepalive 间隔”的量级：正常客户端每 15 秒至少能收一个字节，连续 180 秒一帧都写不出去，只可能是对端没了。这个值不要设得太接近心跳间隔，否则弱网下正常抖动就会被误杀。

时间戳扫描仍然有用，但定位要改：它是指标，不是回收手段。last_write_at 用来在监控上看出”这条连接已经 30 秒没动了”、用来排障时判断是谁的问题，不要指望它释放资源。

清理逻辑还有个位置必须写对：客户端断开时 ASGI 服务器取消生成器，抛的是 asyncio.CancelledError，从 Python 3.8 起它继承自 BaseException。写在 except Exception 里的清理永远不会执行。

8. 多实例：Redis 只是喇叭

部署两个副本后开始出现两类怪事：有的用户刷新后序号跳了一段；有的用户”有时候能收到实时输出，有时候收不到，要刷新一下才行”。

进程内存不跨实例共享，这套设计里有两处依赖它。

一处是序号。 每个进程的计数器都从 0 开始，”1 号事件”在两个 Pod 里各存在一次。用户在 A 收到 5 号，重连被分到 B，B 说”5 号我有，给你 6 号”——它跳过了一批只存在于 A 的事件。

另一处是连接注册表。 A 上产生的事件，只有 A 知道要推给 A 上的连接。B 上的连接即使看的是同一个 run，也不会因为数据写进了共享存储就自动收到。

这里要明确一件事：Redis 只是喇叭，不是账本。 pub/sub 不持久、不重放、离线订阅者收不到历史。真正的可靠性来自事件日志（或数据库），Redis 只负责把”刚发生的事”实时广播到各实例。把 pub/sub 当日志用，一次断线就会丢一段。

发布顺序是”先写日志，再广播”：写日志决定事件有号可补，广播决定它立刻出现。顺序反了会出现”客户端收到了一个还没进日志的事件”，此时断线，这条补不回来。

9. 终态与发布

9.1 终态先落库，再宣布

有一类假成功很隐蔽：服务端先把 run-finished 推给客户端，再去写数据库，写库失败或者进程刚好退出，页面显示完成，数据库还在 running。用户下次进来看到的是”生成中”，但没有任何东西会再推进它。

顺序必须是：落库 → 再广播。

反过来，如果落库成功但广播失败，客户端读超时后会重连，重连拿到快照就恢复正确状态——这是可自愈的。所以宁可少发一条通知，不可早发一条终态。

9.2 优雅关闭与重连摊平

每次发布，连接数瞬间归零、一秒后冲到远高于平时的峰值。服务端退出时所有连接同时断开，客户端如果不知道”这是服务端主动关的”，就会立刻重连。

关闭要有顺序：先通知，等一下，再退出。

前端收到后不要走常规退避，按服务端给的 retry_after 等，几千个客户端就摊在 10 秒里陆续回来：

滚动发布时这一步特别明显：客户端会持续往”还活着的实例”重连，而不是一窝蜂冲向刚启动、还没预热完的那个。

10. 可观测性：先分清连接问题和任务问题

页面卡住时，第一个要回答的问题不是”连接怎么了”，是”任务到底跑完没有”。
查数据库里的 Run 状态：

  • 已经是终态，页面还在转 → 连接问题。查 reader.read() 是否挂着、读超时有没有配、keepalive 是否正常。
  • 还是 running，日志也在推进 → 任务问题。查执行者、工具调用、外部依赖。
  • 还是 running，但日志不推进 → 执行者可能已死。查孤儿任务、进程重启记录。

这个顺序能省掉大量无效排查。反过来先查连接，会在一个健康的连接上耗很久。

三组指标值得单独盯：

  • 连接侧：活跃连接数、平均存活时长、重连次数、读超时触发次数。
  • 事件侧：每秒事件数、durable/transient 比例、补发条数、resync 触发次数。
  • 任务侧：Run 从 queued 到终态的耗时分布、终态先于落库的异常计数（这个应该是 0）。

resync 触发次数是一个很好的健康指标：它升高说明保留窗口不够长，或者客户端断线时间变长——两种都值得查。

上面所有代码都在 Python 3.13 + FastAPI 0.139 + Node 25 下实际跑过（不是示意）：快照优先、序号补发、[DONE] 收尾、401/404 分支、以及”已完成 run 补发后立即收尾”都验证过。有两个坑是跑起来才发现的，写在这里省你一次调试：

  • StreamingResponse 的响应对象构造失败时生成器根本不会启动，它的 finally 不执行——连接会一直占着配额。必须在构造处补一次注销，或者把注册移到生成器内部。
  • 客户端游标超前于服务端最新序号时，会静默卡死：服务端没有未来的事件可补，客户端又把后续事件全当重复丢掉，而 keepalive 让读超时永不触发。必须有 resync 分支，见第 5.1 节。

12. 代价与边界

这套东西不是免费的。它换来的能力是”任务不随连接死”，代价是一整套 Run 存储、执行者、恢复协议。以下场景不值得这么做：

  • 任务秒级结束：用户不会刷新，也不会有半开连接的窗口，普通请求 + 轮询更省。
  • 单用户本地工具：没有多实例、没有代理、没有严格的连接配额，可靠性要求可以降一档。
  • 不需要历史的后台通知：丢了不心疼，pub/sub 就够了，不需要序号和日志。
  • 上行频繁：需要客户端在通道里持续发指令时，SSE 的单向假设不成立，该考虑 WebSocket。
    还有一条边界要说清楚：这套机制保证的是”最终能看到正确状态”，不是”一次都不丢”。 瞬时事件会丢，连接会断，重连会重复。所有保证都建立在”durable 事件可补 + 快照可重建”之上。设计时要先回答：你的事件里，哪些丢了无所谓？

13. 结语

回到开头那个场景：任务在数据库里已经完成，页面还显示”生成中”。这不是某一行代码写错了，而是三件事没有分清楚由谁负责。
任务归任务。 它活在数据库和后台执行者里，不随任何一条连接的生死变化。刷新、断网、换设备，丢掉的只是观察窗口。
连接归连接。 它只负责”把当前状态推给当前窗口”。断了就换一个窗口继续，不需要知道任务历史。
发现异常归客户端。 服务端只能保活和回收资源；真正那双发现”对面已经没了”的眼睛，在客户端，靠的是 45 秒读超时和序号校验。
这三条定下来，参数才有意义：keepalive 15 秒配读超时 45 秒，退避 500 毫秒起、封顶 8 秒，保留窗口 2000 条。数字会随规模变，那三条边界不会。
最后一句：SSE 只负责实时，不负责可靠。 可靠性是序号、快照和读超时三样东西拼出来的，协议本身不提供。
