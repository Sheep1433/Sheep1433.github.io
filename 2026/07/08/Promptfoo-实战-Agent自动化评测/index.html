Promptfoo 实战：从零搭建 Agent 自动化评测体系

发表于 2026-07-08 更新于 2026-07-16 分类于 AI Agent 阅读次数： 本文字数： 3.5k 阅读时长 ≈ 13 分钟
基于 Noesis 项目的实战经验，介绍如何用 Promptfoo 搭建 Agent 的自动化评测门禁——从配置驱动、Python 断言、覆盖度评分到 CI 集成，覆盖完整落地链路。

在做 Noesis 测试用例 Agent 时，我遇到一个很实际的问题：改了 Prompt 模板或者中间件之后，怎么确定 Agent 输出是变好了还是变差了？

靠人肉看几条 case 不靠谱——今天觉得不错，明天换个角度就觉得不行。需要一套能量化、可重复、跑得动的离线评测。

调研了一圈评测框架（DeepEval、RAGAS、LangSmith、Braintrust），最后选了 Promptfoo。理由很简单：配置驱动 + 支持 Python 自定义断言 + 本地就能跑，不需要额外部署一套 SaaS 平台。

这篇文章不讲 Promptfoo 的完整功能清单，而是围绕 Noesis 里一套真实的评测管线，聊清楚怎么把 Promptfoo 用到 Agent 场景里。

先看全景：Noesis 的 6 条评测线

Noesis 的评测包放在 backend/evals/ 下，不搞大一统的跑分入口，而是按场景拆成独立子模块：

场景 评测框架 评什么
测试用例 Agent Promptfoo L0 格式 + 测试点覆盖 recall/precision
RAG 通道 Promptfoo Recall@3 / Hit@3 / 文档注入
BrowseComp Agent 自研 多步检索 + 短答案 accuracy
Terminal-Bench Harbor CLI 终端任务执行
消息压缩 自研 五维 rubrics（accuracy/artifact/context/continuity/completeness）
知识库检索 自研 Recall@K / Hit@K

其中测试用例 Agent 的评测线最能体现 Promptfoo 的设计思路——把 Agent 当黑盒 provider，用金标准数据集 + Python 断言做裁判。

Promptfoo 怎么工作

先快速过一下 Promptfoo 的核心概念，方便后面看代码时对得上号。

配置驱动，不写胶水代码

Promptfoo 的入口是一个 YAML 文件（promptfooconfig.yaml），你只需要声明三个东西：

  1. Provider — 谁生成输出（可以是 LLM API、本地脚本、HTTP 接口）
  2. Tests — 测什么（每条 case 的输入变量 + 期望）
  3. Asserts — 怎么判对错（内置断言 or Python 自定义）

一行命令跑完所有 case 并输出结果 JSON。想可视化就 npx promptfoo@latest view，浏览器里就能翻每条 case 的得分和输出。

内置断言 vs Python 断言

Promptfoo 内置了 equals、contains、is-json、llm-rubric 等常见断言，基本够用于简单 LLM 输出打分。

但 Agent 场景的输出远不止一段文本——往往是结构化 JSON、工具调用序列、甚至副作用（文件生成、状态变更）。这时候内置断言就不够用了，需要 Python 断言：

实战第一步：定义评测配置

测试用例 Agent 评什么

Noesis 有一个测试用例 Agent，输入是需求文档（PRD），输出是结构化的测试场景和测试点。评测它需要回答三个问题：

  1. 格式对不对（L0）——输出是不是合法的 JSON，有没有缺必要字段
  2. 覆盖全不全（Recall）——金标准测试点里，Agent 命中了多少
  3. 生成准不准（Precision）——Agent 生成的测试点，是不是真的 PRD 里有依据

关键设计决策：

  • Provider 不走 LLM API 直连，而是调 Noesis Agent——这样才能评测 Agent 的完整链路（中间件、RAG、沙箱），而不是裸模型
  • 金标准测试点通过 vars 注入每条 case，在自定义断言里用确定性算法做 Token 对齐，辅以 LLM 仲裁 borderline
  • 每条 case 独立，互不干扰，方便排查单条 regression

20 条 PRD 金标准

评测集的 20 条 PRD 覆盖了常见的业务系统功能：登录、上传、审批、支付、权限、消息通知等等。每条 PRD 都配有 15~25 个金标准测试点，由测试工程师评审通过后入库。

实战第二步：写 Python 断言

这是整个评测体系里最核心的部分。Promptfoo 在跑完每个 case 后，会把 Agent 的输出和 context（含 vars、metadata）传给 Python 断言函数，函数返回 {pass, score, reason} 三元组。

L0：格式校验

最基础的一层——输出得先是个合法的结构，才谈得上下一步的覆盖度和准确性。

L0 是硬性门禁——这条过不了，后面的 recall/precision 再高也没意义。

Recall：Token 对齐 + LLM 仲裁

Recall 衡量的是”金标准测试点被覆盖了多少”。核心难点是语义匹配——Agent 生成的 point_name 和人工写的金标准，措辞可能很不一样，但说的是同一件事。

Noesis 的做法是确定性 Token 算法负责大部分匹配 + LLM 只仲裁模棱两可的 borderline，兼顾速度和准确性：

Token 提取做了中英文混合处理——英文关键词取小写、中文按 2-gram 切分，同时过滤掉”测试””功能””流程”这类过泛词。三层判断下来，CERTAIN 匹配占了大多数，只有少数模糊 pair 才会走到 LLM 仲裁：

这样设计的好处：成本可控——20 条 case、每条 20± 个金标准测试点，确定性算法筛掉 80%+ 的明确 case 后，LLM 仲裁量很低；可审计——明确的匹配规则有迹可循，不会出现”不知道为什么这条判过了”的情况。

Precision：双重校验防止幻觉

Precision 衡量的是”Agent 生成的测试点有没有依据”。判定分两层：

  1. 金标准匹配——如果能跟任意金标准测试点匹配上（CERTAIN 或 LLM 仲裁通过），算有效
  2. PRD 文档支撑——匹配不上时，退一步检查生成的 point_name 里关键词是否在原始需求文档中出现

加上第二层校验的原因：Agent 有时会”过度生成”——不在 PRD 范围内的功能点也写出来了。只有金标准匹配是不够的（金标准未必穷尽），但完全不加约束又会有幻觉。PRD 文档 Token 支撑作为一个兜底机制，让合理的额外输出不至于被误判为无效。

实战第三步：把 Agent 接成 Promptfoo Provider

Promptfoo 缺省 provider 是直接调 LLM API（OpenAI、Anthropic 等）。但要评一个 Agent 而非裸模型，需要把 Agent 包装成自定义 Provider：

这里有两个细节值得注意：

  1. 调的是 Agent 图节点，不是裸 LLM——generate_scenes_testpoints_node 是 LangGraph 中的一个图节点，它内部有自己的 prompt 模板、RAG 召回、输出解析。Provider 只是一个薄壳，下面的 Agent 全链路才是真正的评测对象。

  2. 每条 case 的 Langfuse trace 独立——eval_langfuse_run 是临时注入 Langfuse 环境变量的上下文管理器（评测用的 Langfuse 项目与生产隔离），退出后恢复原值。这样既能做 trace 回溯，又不会污染生产环境的追踪数据。

背后做的事：

  1. 解析 promptfooconfig.yaml，找到 provider 和 tests

  3. 对每条 case，调 provider.py:call_api，拿到 Agent 输出

落地建议

1. CI 集成

Promptfoo 评测的核心价值不是”跑一次看看”，而是每次改动都跑一遍，防止退化。最简单的 CI 集成：

设一个阈值：如果 recall 或 precision 相比 baseline 下降超过 5%，CI 标红，迫使开发者关注是什么改动导致的。

2. 评测集维护

评测集会腐化——业务变了、Agent 行为变了，旧的金标准可能不再适用。建议：

  • 每次 PRD 评审通过的测试用例，挑有代表性的补充进评测集
  • 定期跑一遍，标记长期低分 case，判断是 Agent 的问题还是评测集该更新了
  • 金标准保持 20-50 条，太少覆盖不全，太多维护成本和跑分时间涨得快

3. 避免的坑

  • 别用 LLM 断言替代所有确定性规则——LLM 会波动，同一个 case 跑两次分数不一样。能用 Token 匹配、子串包含解决的，就别上 LLM。只把 LLM 留给确定性算法搞不定的 borderline。
  • Provider 要走 Agent 全链路，不是裸 LLM——否则中间件、RAG、工具调用这些环节出了 bug，评测是测不到的。
  • Python 断言里接 Agent 时要处理好超时——maxConcurrency: 1 避免并发把 Agent 或 LLM API 打爆。

写完这篇文章回头看，Promptfoo 本质上是一个”重配置、轻代码”的评测编排引擎——它的价值不在于多高级的 scoring 算法，而在于把 provider、tests、asserts 解耦，让你可以专注于写真正有区分度的断言逻辑。

Noesis 里的自定义断言 + 确定性 Token 对齐 + LLM 仲裁的组合，实际跑了上百次，稳定性和区分度都不错。如果你的 Agent 也有类似的结构化输出（JSON → 断言），这套模式可以直接搬过去用。
