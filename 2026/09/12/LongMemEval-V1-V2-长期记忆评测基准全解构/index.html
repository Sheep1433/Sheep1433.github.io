LongMemEval V1→V2 全解构：从 500 条对话到 1.15 亿 token 轨迹的长期记忆评测

发表于 2026-09-12 更新于 2026-09-14 分类于 AI Agent 阅读次数： 本文字数： 6.7k 阅读时长 ≈ 24 分钟
逐字段拆解 LongMemEval V1 的 question JSON 与索引对齐、V2 的轨迹目录与五类记忆问题，还原 Insert/Query 评测协议、AgentRunbook-R/C 两条 baseline 的运行机制，并推导 LAFS 延迟调整分数的积分公式。

LongMemEval 评测的是这样一件事：把一段漫长的历史交互只允许经过一次顺序写入交给你的记忆系统，然后在每个问题上，系统在有限 token 预算内取回证据，交给一个固定的阅读模型作答，答对了才算记忆有效。V1（ICLR 2025）用 500 道题、115k～1.5M token 的对话干草堆考 chat assistant 的长期交互记忆；V2（arXiv 2605.12493）把考卷换成 451 道题、最高约 1.15 亿 token 的多模态 Agent 轨迹，并把准确率与查询延迟压成一条曲线下的面积——LAFS。

这两个版本出自同一个作者组（Di Wu、Kai-Wei Chang 等），可以当成同一评测哲学在两个时代的投影：从「模型能不能在长历史里找到那句话」变成「记忆系统能不能让 Agent 变成一个有经验的同事」。这篇文章逐字段、逐脚本地把两个版本拆开：数据格式、索引对齐、Harness 协议、baseline 内部实现、Judge 打分和 LAFS 公式。

文中所有字段名、文件名、超参数都对照官方仓库与论文核实过（V1：arXiv 2410.10813、github.com/xiaowu0162/LongMemEval；V2：arXiv 2605.12493、github.com/xiaowu0162/LongMemEval-V2），部分数据细节是我拿本地 cleaned 版文件逐条数出来的。

一、范式演进：V1 vs V2

维度 LongMemEval-V1（ICLR 2025） LongMemEval-V2（2026）
记忆对象 用户与助手的跨会话聊天历史 多模态 Agent 操作轨迹（WebArena + WorkArena）
题量 500 questions 451 questions
干草堆规模 S 档 115k token（30–40 会话）；M 档 ~1.5M token（500 会话） Small 档 100 条轨迹 ~25M token；Medium 档每题最多 500 条轨迹 ~115M token
模态 纯文本对话 目标/动作/结果文本 + 每步无障碍树（AXTree）dump + 每步截图
被测对象 模型 × 记忆组织方式（阅读端可变） 记忆系统本身（阅读模型钉死为 Qwen3.5-9B）
评估输出 LLM-judge 二值准确率 + 检索 Recall@k / NDCG@k 分题型准确率 + 查询延迟 → LAFS 单一分数
数据来源 属性控制的针中藏针合成会话（证据）+ ShareGPT/UltraChat/仿真会话（填充） AgentLab harness 采的 1,540 条真实轨迹（成功率 52%）

规模差了两个数量级：V1 的 M 档全量历史约 1.5M token，已经超出当时所有模型的有效上下文；V2 的 Medium 档干草堆约 1.15 亿 token，任何「塞进上下文窗口」的方案从定义上就出局了，评测强制退化成检索与压缩问题。

更关键的变化在被测对象上。V1 论文的实验口径是「同一个模型，换不同的记忆组织方式再读」（全历史直读 / 会话分解检索 / 时间感知检索等），被测的其实是模型的长历史阅读能力；社区（Mem0、MemOS、Zep 等）后来把它当系统级 benchmark 用——你的记忆系统吃进 haystack_sessions，吐出检索结果。这两种口径的分数不能直接比，这是 V1 榜单上最常见的混淆。V2 把话说死了：阅读模型固定为 Qwen3.5-9B（vLLM 部署，temperature 0.6、top_p 0.95、top_k 20、关闭 thinking），所有准确率差异只能来自记忆系统返回的证据质量。控制变量的思路从论文评审搬进了 harness。

模态描述上有个流传很广的说法是「文本 + DOM 树 + 截图」。官方实现里不是 DOM：每步状态保存的是 text 字段——一份 AXTree dump（无障碍树，即页面控件的角色/名称/状态的结构化文本表示），加一张对应截图。「DOM」是转述时混进来的词，写 harness 时照它去抓页面结构会走弯路。

二、V1 数据格式：500 个 JSON 对象的解剖

2.1 单条 question 的字段结构

longmemeval_s.json / longmemeval_m.json / longmemeval_oracle.json 三个文件各是一个含 500 个对象的 JSON 数组。节选一条（内容截断，字段顺序与官方数据一致）：

字段逐个说：

字段 类型 作用
question_id str 唯一 ID；拒答题以 _abs 后缀标识（如 0862e8bf_abs），拒答不是一种 question_type，而是叠加在原题型上的标记
question_type str 6 个取值：single-session-user / single-session-assistant / single-session-preference / temporal-reasoning / knowledge-update / multi-session
question str 题面
question_date str 提问时间戳，格式 %Y/%m/%d (%a) %H:%M——时间推理题的锚点
answer str 标准答案；single-session-preference 题存的是判卷 rubric 而非唯一答案
answer_session_ids list 证据会话 ID，全部以 answer_ 前缀标识；500 题合计 948 个证据会话（均值 1.9，最多 6）
haystack_dates list 每个历史会话的时间戳，与下面两个数组按下标对齐
haystack_session_ids list 会话 ID；前缀泄露来源——answer_ 是证据会话，sharegpt_ / ultrachat（形如 85a1be56_1）/仿真会话是填充物
haystack_sessions list[list] 会话本体，每个 turn 是 {role, content}；含证据的 turn 额外带 "has_answer": true

填充物构成有公开配方：25% ShareGPT、25% UltraChat、50% 与用户画像一致的仿真会话；S 档填充上限 80 个会话并设 115,000 token 的 JSON 长度帽，M 档上限 500 个。

2.2 索引对齐：三个平行数组如何拼出「带时间戳的历史」

V1 最容易被忽视、又最容易写错的设计是：三个等长数组按数组下标描述同一个会话，500/500 条数据里长度严格相等：

这带来两个工程后果。第一，会话隔离与时间标定是免费的：不需要解析会话内容里的任何时间信息，每个会话的「何时发生」由 haystack_dates[i] 直接给出，时间推理题考的是「文本内显式时间表达 + 元数据时间戳」的联合推理，不是考模型找时间。第二，检索评估可以做到两级粒度——会话级用 answer_session_ids，turn 级用 has_answer 标记（全数据集共 896 个证据 turn）。

我自己核对 cleaned 版数据时发现一个 README 没写的坑：官方说 _s/_m 的会话「按时间戳排序」，实际 500 条里有 211 条在同一天内存在乱序（比如 15:24 之后跟着 01:34），做到分钟级非降序的只有 289 条、严格递增的只有 249 条。如果你的 harness 假设「数组尾部就是最新会话」做 recency 截断，会截错。另外 question_date 晚于全部历史时间戳这条设计（论文记作 t_q > t_N），实测只对 424/500 成立——直接拿这两条做不变量断言会翻车。

2.3 五大能力与六种题型的映射

论文定义的五个核心能力，落到数据上是六种 question_type 加 _abs 标记。cleaned 版 S 档的真实分布（我逐条数的）：

能力 题型载体 题量 考什么
Information Extraction（IE） single-session-user 70 从单个会话里提取用户自述的事实
Information Extraction（IE） single-session-assistant 56 提取助手曾给出的信息（换述后不能丢）
IE / 个性化 single-session-preference 30 用户偏好总结，按 rubric 判卷，无唯一答案
Multi-Session Reasoning（MR） multi-session 133 一题的证据散在多个会话，需关联后推理
Knowledge Updates（KU） knowledge-update 78 事实随时间被更新（换工作、改偏好），必须用最新值回答
Temporal Reasoning（TR） temporal-reasoning 133 结合时间戳与文本内时间表达做推算（「结婚时 Rachel 多大」这类）
Abstention（ABS） question_id 带 _abs 30 错误前提下拒答；横跨 multi-session 12 / single-session-user 6 / temporal-reasoning 6 / knowledge-update 6

顺带纠正两个流传的说法：其一，不少转述给 V1 编了一套「子类分类法」（needle/cross-session、arithmetic/scope filtering/edit propagation 之类）——论文和仓库里都不存在这套词，TR 在数据生成阶段只有 temp_reasoning_implicit / temp_reasoning_explicit 两个内部任务名，没有正式发表的子类。其二，V1 没有「L 档」：HF 上只有 _oracle / _s / _m 三个文件，M 档就是 ~1.5M token，不存在 1.1M 的第三档。给 V1 评分的 J score 也不是 LongMemEval 的指标——那是 Mem0 论文（arXiv 2504.19413）在 LOCOMO 上的 LLM-as-a-Judge 指标。

还有两个文件变体值得知道：longmemeval_oracle.json 只保留证据会话（去填充物），用于测「检索完美时」的阅读上限——论文里 GPT-4o 的 oracle 分是 87.0%，这就是这套题的天花板；以及 2025/09 官方用 longmemeval-cleaned 替换了原版 HF 数据集（清除了干扰答案正确性的历史内容），拿旧版跑出的分数和 cleaned 版没有可比性。

三、V2 数据格式：轨迹目录与五类记忆问题

3.1 轨迹的物理结构

V2 的干草堆不再是 JSON 数组里的会话列表，而是磁盘上的轨迹目录：

trajectory.json 的字段（截图路径与状态按下标对齐，和 V1 的三数组对齐是同一个思想）：

states[].text 就是 AXTree dump——几十条轨迹加起来上亿 token 的主要来源；states[].screenshot 是路径引用，截图本体在 screenshots/ 下按 <trajectory_id>/<step>.png 组织。数据脚本链是 data/download_data.py → prepare_data.py（解包截图）→ validate_data.py。

数据集本身的一些硬数字：1,540 条轨迹（WebArena 599 + WorkArena 941），由 AgentLab harness 用 ReAct 式 Agent 采集（GPT-5-mini 73.1% / GPT-5.2 22.9% / Codex-GPT-5.2-xhigh 4.0% 的混合，整体成功率 52.0%，平均每条 28.1 个状态）。每道题平均需要 1.4 条答案轨迹（最少 1，最多 5）。

3.2 五类记忆问题

V2 论文用「有经验的同事」做比喻定义五类问题，这是它和 V1 最深的一次范式转变——考的不再是「记得用户说过什么」，而是「从长期操作中学到了什么」：

类别 论文定义（意译） 典型问法
Static State Recall 记得环境里的重要地标、页面布局、控件用途，以及状态间的细微差别 「商品列表页每页显示多少条结果？」
Dynamic State Tracking 能充当环境的世界模型：给定状态与动作，理解环境如何随之变化 「把商品加进愿望单之后，愿望单图标会怎么变？」
Workflow Knowledge 知道在这个定制环境里完成常见任务的步骤 「在后台取消一张订单，完整流程是什么？」
Environment Gotchas 意识到环境里的常见坑，能避开环境特有的失败模式 题面伪装成新手带着截图求助：「这一步为什么总是报错？」
Premise Awareness 识别出「在别的环境成立、在这里不成立」的前提假设 错误前提 + 截图，必须指出前提错误（题型带 -abs 后缀，是 V2 的拒答题）

题型实现上分三种：判断题、多选题、短答题。Premise Awareness 是显式的 abstention 题；Gotchas 题以「新手发消息求助 + 截图」的情景出现，考的是你有没有把过去踩过的坑变成可迁移的告诫。

四、评测 Harness 与 API 协议

4.1 Context Gathering：两个方法，四步流水线

V2 的评测范式叫 context gathering：不评 Agent 的端到端任务成功率，只评记忆系统能否为下游问答产出紧凑证据。任何记忆后端（官方叫 memory module）继承同一个基类并用装饰器注册：

协议有个容易低估的设计：隐私隔离。后端在整个评测过程中拿不到任何 benchmark 元数据——没有题目 ID、题型、标准答案，query() 收到的除了问题文本（和可选截图）只有一个随机 query_invocation_id（通过 self.get_query_context() 获取）。仓库里有专门的 tests/test_query_privacy.py 钉住这一点，防止后端「认识题目」作弊。

Harness 的四步流水线：

第③步的 token 预算由 --memory-context-max-tokens 控制（默认 200,000），计数器是 Qwen3.5-9B 的 chat 模板 processor，图片按 PIL 尺寸折算——也就是说截断标准和阅读模型的真实 tokenizer 完全一致，不存在「按 GPT 的 token 数估的预算在 Qwen 侧爆窗」。超预算的上下文不是粗暴砍尾，而是二分搜索最大可容纳前缀再截断。第②步还有个共享优化：Small 档所有题共用同一干草堆，memory 实例只构建一次并被线程安全共享；RAG/Codex/AgentRunbook 这类每题需要独立工作区的后端则走每题独立 workspace 路径。

4.2 AgentRunbook-R：三池 RAG baseline

memory_modules/agentrunbook_r.py（注册名 agentrunbook_r）是官方的「结构化 RAG」上限参考。插入阶段把每条轨迹拆进三个知识池：

池 内容 生成方式
Raw Slices（原始切片） 以某状态为中心、半径 1 的连续状态窗口（AXTree 文本 + 截图） 纯机械切分，embedding 索引在 slice_axtree_text 上
Transition Events（转移事件） 每次状态转移一条事件，JSON {"overview": "...", "state_transition": "..."}，ID 形如 event_0012_0013 LLM 逐转移描述；插入阶段异步并发（EVENT_ASYNC_MAX_CONCURRENCY = 16）
Strategy Notes（策略笔记） 每条轨迹两条：一条 procedure note（操作流程）、一条 hint note（坑与提示） LLM 事后总结

三池落盘为 agentrunbook_r_artifact/ 下的 raw_state_pool.jsonl、event_pool.jsonl、.npy embedding 和 artifact_index.json，带 SHA-256 指纹防串改。

查询时是一个 Qwen3.5-9B 控制器先改写问题、再向量检索的流程。控制器输出一份结构化查询计划：

raw_state_queries 最多 5 条、每个不同 UI 界面一条。三路计划用 Qwen3-Embedding-8B 做稠密余弦检索，超参数：事件取 top-6、笔记取 top-3、原始切片预算 6 个且单查询上限 m = min(2, 6 // n_queries)。可选再来一轮 LLM rerank（输出 {"selected_indices": [...], "selection_description": "..."}）。最终上下文渲染成三个 markdown 区块（”## Procedure and Hint Notes Learned from Previous Tasks in the Environment” 等）交给 reader。

有个说法需要修正：不少转述称三路检索「并发执行」。官方实现里查询侧是顺序执行的（改写→检索→可选 rerank 串行），并发只存在于插入侧的事件生成和 harness 层。它 Small/Medium 档的公开成绩是 58.6% / 57.0%，延迟 26.9s / 25.8s。

4.3 AgentRunbook-C：把记忆检索变成沙盒里的编码任务

agentrunbook_c.py 继承自 Codex 基类，思路是：既然轨迹已经在文件系统上，就让一个 coding agent 在沙盒里主动翻文件来答检索。每次 query() 构建独立沙盒：

inspect_trajectory.py 的用法（INSTRUCTION.md 里教给 agent）：

INSTRUCTION.md 的约束写得很工程化：要求 agent 把自己当「快速记忆检索模块」，先对问题做 triage，禁止基于数字序列、相邻行、相似按钮外推（do not extrapolate from numeric progressions, nearby rows, similar buttons）——这条是针对 RAG/LLM 检索常见的「证据近似就编」失败模式设计的。

答案不写自然语言自由文本，而是写回结构化的 memory_module_output.json：

memory_markdown 固定两个 section：## Support Analysis（必须明确说出问题前提是否成立——这是给 Premise Awareness 题留的接口）和 ## Relevant Procedure and Hint Notes。trajectory_spans 是零基、闭区间的证据指针，全题合计最多 20 个状态、单个 span 通常 ≤3 步。harness 会校验 span 合法性（越界 span 拆出），然后把 span 连同 goal、URL、动作、AXTree 文本、截图渲染进 reader 上下文——「摘要 + 可回溯指针」的双层输出，是它比朴素 RAG 少犯 reader error 的直接原因。

底下的 Codex 基线（codex.py）则不给任何脚手架，直接 subprocess.Popen 拉起一个真实 CLI：

超时 1800s（轮询 0.25s，SIGTERM 后 5s 宽限再 SIGKILL 整个进程组），每查询最多 3 次尝试，stdout/stderr/events/usage/duration 全量落审计日志。注意它不是 tmux——常见转述里的 tmux 多路复用方案在官方仓库里不存在，进程编排就是一个带进程组的子进程。

四个 baseline 在两个档位的结果（论文口径，LAFS 参考前沿的原始数据）：

方法 Small 准确率 Small 延迟 Medium 准确率 Medium 延迟
RAG query→slice + notes 51.0% 0.2s 45.9% 0.3s
AgentRunbook-R 58.6% 26.9s 57.0% 25.8s
Codex（裸 CLI） 69.9% 177.2s 68.7% 185.8s
AgentRunbook-C 74.9% 108.3s 70.1% 139.9s

这张表里藏着一个关键事实：Codex 比最强 RAG 高 18 个百分点，但延迟 700 倍；AgentRunbook-C 用 manifest 粗筛 + helper 脚本换来了「比 Codex 再高 5 个点、还快 32%」。准确率和延迟不是免费互换的，脚手架质量决定 Pareto 前沿的位置——这正是 LAFS 存在的理由。

五、评测执行与 Judge 打分

5.1 Harness 运行机制：三遍式，不是多进程分片

evaluation/harness.py + run_eval.py 的执行结构是三遍顺序推进，而不是网上说的「多进程分片 + tmux」：

  1. Prompt 构建遍：为每题调 memory.query() 组装消息。可配 ThreadPoolExecutor(prompt_build_max_workers) 并行；共享干草堆时 memory 单实例共享，非共享型后端每题独立 workspace（跑完由 compact_nonshared_memory_workspace 清掉没用到的轨迹文件）。
  2. Reader 生成遍：全异步——asyncio + AsyncOpenAI，并发由 asyncio.Semaphore(reader_max_concurrent_requests)（默认 500）控制，max_retries=10，BadRequestError 降级为空响应不中断整批。图片以 base64 data URL 进多模态消息。
  3. 打分遍：顺序执行。

查询延迟用 time.perf_counter() 包住 memory.query()（含 post_query_hook）计时，聚合成 avg/p50/p95/max 写进 aggregated_metrics.json，每题明细进 per_question.jsonl；两个 domain（web/enterprise）由 combine_aggregated_metrics.py 按题量加权合并。SIGINT/SIGTERM/SIGHUP 被改写成 cancel_event，memory 后端观测它做优雅取消——长时间跑 451 题时 Ctrl-C 不会留下一堆半写状态。运行入口是 evaluation/scripts/run_agentrunbook_r.sh 这类脚本，输出目录形如 runs/no_retrieval_web_small，memory 配置经 --memory-config-path 传入 evaluation/memory_configs/*.json。

5.2 V1 的 Judge：按题型分 prompt 的 GPT-4o

V1 的打分脚本是 src/evaluation/evaluate_qa.py，用法：

判卷模型 gpt-4o-2024-08-06，temperature 0、max_tokens 10，输出 yes/no 二值标签，准确率即标签均值，另按 question_type 分桶。与人类专家的一致率 97–98%（判 GPT-4o 答案 0.98，判 Llama-3.1-8B 答案 0.97，abstention 0.97/0.90）。

值得细看的是判卷 prompt 按题型定制这件事，四个例子：

  • temporal-reasoning：不因天数差一惩罚——问「多少天」答 45 而标准答案 46，判对；
  • knowledge-update：回答里允许残留旧信息，只要新答案在场——考的是「知不知道最新值」，不是「忘没忘掉旧值」；
  • single-session-preference：对着 rubric 判，容忍合理的偏好表述差异；
  • abstention（_abs 题）：单独的 prompt，判「模型是否正确识别该问题不可答」，输入是问题 + 不可答原因 + 模型回答。

检索质量另有一套指标：用 answer_session_ids 和 has_answer 算会话级与 turn 级的 Recall@k / NDCG@k，30 道 _abs 题不参与检索评估（它们没有「该召回什么」的正确答案）。检索指标和准确率分开看是这套 benchmark 最实用的用法——我们跑 20 题子集时，答案准确率 70% 的主要损失在时序推理（8 题对 4 题），而检索 precision 有 0.85：证据送到了、reader 算错了，和证据根本没送到，是两种完全不同的修复方向。

5.3 V2 的打分：能规则的规则，不能规则的才给 GPT-5.2

V2 的打分链比 V1 冷静得多。答案必须装箱（extract_boxed_answer 解析），然后分两路：

  • 结构化题（多选、短答）走确定性评估器——归一化短语匹配、保序短语匹配，零模型调用、零判卷方差；
  • 只有 Gotchas 和 abstention 两类交给 Judge：llm_gotchas_checker / llm_abstention_checker，GPT-5.2（medium reasoning），输出二值 JSON 标签。

还有一条硬规则：在非拒答题上给出 abstention 式回答，强制判错——「不放心就拒答」在 V2 里不是安全牌。leaderboard 上的指标因此是分题型的：static_accuracy、dynamic_accuracy、procedure_accuracy、gotchas_accuracy 加 abstention，再合成总分。

5.4 LAFS：把「快而准」压成一个数

单看准确率，RAG 的 0.2s 和 AgentRunbook-C 的 108s 没法比；单看延迟又会奖赏烂检索。V2 的解法是 Latency-Adjusted Frontier Score：在 1s 到 200s 的对数均匀延迟预算上，积分「该预算内可达的最佳准确率」，再除以积分区间长度。实现就在 leaderboard/compute_lafs.py，核心常量 T_MIN = 1.0、T_MAX = 200.0、FLOOR_ACC = 0.0。

拿 Small 档参考前沿手算一遍。四个 baseline 点：(0.2, 51.0)、(26.9, 58.6)、(108.3, 74.9)、(177.2, 69.9)。第四个点被 (108.3, 74.9) 严格支配（更慢且更不准），Pareto 前沿剩三个点。积分区间与取值：

对数区间 预算内最佳准确率
[1, 26.9] 51.0（0.2s 的 RAG 已在预算内）
[26.9, 108.3] 58.6
[108.3, 200] 74.9

Leaderboard 的实际用法是增量制：提交方可给多个延迟工作点（标注 fast / balanced / accurate），提交增益 = LAFS(F_ref ∪ S) − LAFS(F_ref)，即你的点对固定参考前沿（上表四点）的边际贡献。想在快区拿分，就得有 1–27s 内超过 51% 的方法；想在慢区拿分，得在 200s 内打过 74.9%。Codex 那个 177.2s 的点对参考前沿贡献为零——被支配的点无论多准都不产生 LAFS 增益，这就是这个指标对「盲目堆延迟」的惩罚。

六、跑这套基准时容易踩的坑

拿本地数据核对加实测跑分，攒下这些容易翻车的点：

  1. **V1 要用 longmemeval-cleaned**。原 HF 数据集已标 deprecated（2025/09），旧版分数与 cleaned 版不可比；两版的差异在官方 Google Sheets changelog 里。
  2. 别假设会话数组分钟级有序。README 说 sorted by timestamp，实际 cleaned 版只有 289/500 严格递增，同天有乱序；question_date 晚于全部历史也只对 424/500 成立。做 recency 截断或时间不变量断言前先自己数一遍。
  3. _abs 题在 judge 和检索两个环节都特殊。判卷走单独的「是否正确拒答」prompt；检索评估直接跳过。把它混进普通题算 recall 会污染指标。
  4. V2 的 token 预算按 Qwen3.5-9B 的 tokenizer 计（默认 200k，图片折算在内），用别的 tokenizer 估预算会错位；截断是二分最大前缀，不是砍尾。
  5. 小样本子集的置信区间宽得吓人。20 题二项 70% 的 95% 置信区间宽达 46%–88%（Clopper-Pearson 精确区间），拿它和别家全量分数并排做表时必须写明口径。
  6. V2 后端拿不到题目元数据，只有随机 query_invocation_id。想在 query 里按题型分支优化的「捷径」协议上就不存在，test_query_privacy.py 专门堵这个。

小结

LongMemEval 两代合起来讲了一个完整的评测故事：V1 证明了「跨会话事实、时间推算、知识更新、拒答」可以被组织成可复现的数据结构——三个平行数组的索引对齐、has_answer 的 turn 级标注、oracle 上限，这些设计让记忆系统的检索质量第一次可以被独立测量；V2 把同样的严谨性搬到了大两个数量级的多模态轨迹上——固定 reader 隔离记忆系统变量、200k token 预算强制压缩、确定性打分压缩判卷方差、LAFS 把「快」和「准」变成同一条曲线下的面积。

如果要带走一个观察：这套 benchmark 真正测的不是「存了多少」，而是「压缩证据的保真度」——AgentRunbook-C 的高分来自「manifest 粗筛 → helper 精查 → 最多 20 个状态的带指针摘要」这条压缩链，而不是任何花哨的存储结构。想在 LAFS 上拿分，先想清楚你的系统交出去的那份 200k token 以内的证据，是不是每一条都值得 reader 读。
