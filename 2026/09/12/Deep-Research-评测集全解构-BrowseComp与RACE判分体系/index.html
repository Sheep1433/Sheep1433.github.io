DeepResearch Bench 全解构：RACE/FACT 双框架与报告评测的判分体系

发表于 2026-09-12 更新于 2026-09-15 分类于 AI Agent 阅读次数： 本文字数： 4.6k 阅读时长 ≈ 17 分钟
以 DeepResearch Bench 为主角拆解报告型评测：query/criteria/reference 三件套数据格式、RACE 双盲对比与自适应标准的加权公式、FACT 引用可信度流水线、judge 选型成本矩阵与位置偏差问题，附我们自建 harness 跑中文子集与移植官方判分脚本的一手工程细节。

报告型 deep research 评测考的是这样一条链路：给系统一个开放式调研任务，它多步检索、交叉验证、综合成一篇长报告，评测负责回答两个独立的问题——报告内容好不好，以及报告里的事实有没有可信出处。DeepResearch Bench（arXiv 2506.11763，中科大 USTC 与 Metastone Technology 出品，一作 Mingxuan Du，通讯作者为 USTC 的 Zhendong Mao）是目前这套问题的标准参照系：100 道博士级调研任务、逐题定制的自适应评判标准、RACE/FACT 双判分框架，也是唯一把全套判分脚本开源出来的报告基准——我们的评测线（evals.agent.deepresearch）就建在它上面，判分 prompt 用的是官方中文原版。

这篇文章以它为主角：数据格式、RACE/FACT 的完整机制、judge 选型与已知缺陷、我们自己跑分的一手工程细节。开篇先用一节的篇幅把它放进 deep research 评测集的坐标系——不看坐标系，理解不了「为什么报告评测只能这么做」。

一、坐标：报告评测在 deep research 评测集里的位置

deep research 的评测集按答案形态分两派，判分协议由它决定：

「LLM 裁定」和「LLM rubric」的分界在于裁判判什么：裁定输入里有标准答案，裁判只回答「模型答案和它等价吗」，二值输出，没有裁量空间——BrowseComp 的判分 prompt 写到明令禁止的程度：「不要尝试自己解题，不要为任何与标准答案不同的答案辩护」；rubric 输入里只有「什么是好」的定义（标准列表、可能有参考报告），裁判必须行使品味打连续分，于是 judge 换模型分数会漂移、存在位置偏差——这两类问题正是 RACE 协议设计的主线，后面展开。

两派的主流成员一览（供选型定位，本文不再逐个展开）：

评测集 出品 题量 测什么 判分
GAIA HF + Meta，2023 466 通用助手多模态问答 准精确匹配
HLE CAIS + Hendrycks，2025 2,500 百科级专家难题 精确匹配 + o3-mini 核验
BrowseComp OpenAI，2025-04 1,266 多跳网页检索短答案 LLM 裁定（HLE 同款 prompt）
BrowseComp-ZH Peilin Zhou 等，2025-04 289 中文互联网多跳检索 GPT-4o 判卷
BrowseComp-Plus Waterloo 等，2025-08 830 固定语料 100,195 篇内检索 LLM 裁定 + 引用 P/R
DRB FutureSearch，2025-05 89 8 类研究任务（找数字/验证断言…） 按题型确定性计分
xbench-DeepSearch HongShan，2025-05 滚动 100 题 中文深度检索（季度换题） LLM judge
ReportBench 字节，2025-08 100 学术 survey 复现 对 GT 引用集算 P/R
ResearcherBench SJTU/GAIR，2025-07 65 AI 科研前沿咨询 rubric 覆盖率 + 事实双轨
LiveDRBench 微软，2025-08 100 高扇出概念检索 key-claims 抽取 + F1
DeepResearch Bench USTC + Metastone，2025-06 100 开放调研报告（22 领域，中英各半） RACE rubric + FACT 引用核查

三个坐标点帮助理解它的位置。其一，GAIA（2023）是「对人不难、对模型极难」现象的原点：人类标注者 92% 通过，GPT-4 加人工挑选的插件只有 15%——deep research 这个产品形态就是从这个鸿沟里长出来的。其二，短答案派的极限是 BrowseComp：1,266 道人写「倒置谜题」，人类两小时只做出 29.2%（七成放弃），OpenAI 的 Deep Research 做出 51.5% 但校准误差高达 91——对错各半还自信满满；它证明了「检索耐力」可以被做成可验证短答案，但测不了报告。其三，报告派的其他成员各有巧思但都没有成为参照系——ReportBench 用 arXiv survey 逆向出题让文献列表成为天然金标（它揭示了行业短板：OpenAI Deep Research 引用精度 0.385、召回只有 0.033）；ResearcherBench 拿真实科研咨询题做双轨判分；LiveDRBench 不评最终报告、评中间表示（key claims 的 F1）。

DeepResearch Bench 能成为参照系，靠的是三件别家没有凑齐的东西：逐题定制的自适应标准（每题的四维权重和 5–8 条标准都是为该题写的）、相对分设计（和专家参考报告同场对比，抑制 judge 漂移）、全套开源判分脚本（别人给分数，它给尺子）。

二、数据集：三个 jsonl 的分工

100 道任务覆盖 22 个领域（WebOrganizer 分类法，不是转述里常说的 26 个），中英各 50 题（id 1–50 中文、51–100 英文）。题源是 96,147 条匿名真实用户查询，经 DeepSeek-V3-0324 筛出 44,019 条 deep research 型查询，再由 5 年以上经验的博士/从业者出题。参考报告全部是 Gemini-2.5-Pro Deep Research 在 2025 年 4 月的快照——这个时间戳后面判分口径一节会用到。

两个容易被忽略的细节：字段名是拼错的 criterions（官方如此，移植时照抄别「修正」）；每题每维 5–8 条标准、条目权重在维度内归一，四个维度的权重由出题时按任务性质动态分配——insight 通常最重（0.32–0.41），readability 最轻（0.11–0.20）。标准和权重是逐题定制的，这就是 RACE 名字里 “Adaptive” 的含义：综述题的「全面性」和工程方案题的「全面性」不是同一回事，静态 rubric 描述不了。

三、RACE：双盲对比 + 相对分

RACE 的全称是 Reference-based and Adaptive Criteria-driven Evaluation framework with Dynamic Weighting。判分时裁判同时看到两篇报告——被测报告（<article_1>）和专家参考报告（<article_2>）——外加该题的标准列表，逐条标准给两篇各打 0–10 连续分（分段锚点 0–2 / 2–4 / 4–6 / 6–8 / 8–10），并输出对比分析。四个协议级细节：

  1. 引用在判分前剥离——RACE 只评内容质量，引用质量交给 FACT；
  2. 权重不进判分 prompt（只给 criterion + explanation），防止裁判看权重分配注意力——这是我们移植时对着官方代码确认过的行为；
  3. 裁判拿到的只是 <article_1> / <article_2> 编号，prompt 不说明哪篇是参考——但顺序是固定的（官方入口脚本 deepresearch_bench_race.py 里被测报告恒为 article_1、参考恒为 article_2），没有交换顺序取平均之类的位置偏差对冲。RACE 分数里可能存在未被测量的系统性位置偏差；
  4. 单次 LLM 调用完成全部维度的判分，不分组重判。

为什么最后一步做成相对分？因为 rubric 绝对分有严重漂移：换个 judge 模型、换个 prompt 版本，7 分的含义就变了。把专家参考报告拉进来同场对比，「你比 Gemini-2.5-Pro 的报告好还是差」是个跨 judge 更稳定的量。代价也明确：你的分数量化的是「相对 2025 年 4 月的 Gemini 快照」，不是绝对质量——参考报告自己也在老化。

裁判选型论文里给了完整的成本-一致率矩阵（与人类判断的一致率 / 单题成本）：Gemini-2.5-Pro 72.56% / $0.13、Claude-3.7-Sonnet 72.28% / $0.47、o4-mini 71.63% / $0.04、o3 68.58% / $0.37；人类标注者之间的一致率只有 68.4%——最好的 LLM 裁判已经比人类互相之间更一致。论文期 RACE 裁判选了 Gemini-2.5-Pro，2026 年仓库已切到 GPT-5.5（一致率 71.82%），Gemini 代码保留在 Gemini-2.5 分支。历史分数因此跨 judge 版本不可比。

四、FACT：引用的两项指标

FACT（Factual Abundance and Citation Trustworthiness）管另一半：报告里的事实有没有出处、出处撑不撑得住。流水线与 LLM 调用账单（从官方 utils/extract.py / validate.py 源码核实）：抽取 1 次调用（整篇报告进一个 prompt，输出全部「陈述–URL」三元组）→ 程序化去重（同事实同 URL 只留一条）→ Jina Reader 抓取正文（非 LLM）→ 判定每个唯一 URL 1 次调用（该 URL 正文 + 所有引用它的陈述打包进同一 prompt，三值判定 supported / unsupported / unknown，内部最多重试 3 次）。一篇引用 100+ 条陈述的报告，判定调用量等于其唯一 URL 数——比 RACE 高一个数量级，这也是官方用便宜档模型（论文期 Gemini-2.5-Flash，现 GPT-5.4-mini）做 FACT 的原因。两项指标：

人类一致率：支持 96% / 不支持 92%。三个从源码核出的读数细节：unknown 从分母剔除（抓取失败不伤 C.Acc，只是让该陈述退出统计）；supported 标准宽松——陈述的事实「全部或部分」在来源中找到即算，数值接受四舍五入，所以 C.Acc 度量的是「引用没有张冠李戴」而非「每条陈述被完整背书」；每次判定要求裁判返回条数与打包陈述数严格相等，否则整次重试、三次失败则该 URL 全部陈述作废。另外论文公式是逐题平均（无引用计 0），发布脚本 stat.py 算的是全库池化比率且跳过无引用题——移植时照哪个口径要自己定并写明。这两个数与 RACE 是反着用的——C.Acc 高 E.Cit 低是「引得准但引得少」，C.Acc 低 E.Cit 高是「海量引用里混着撑不住的」。

五、移植 RACE 时踩到的坑

我们的评测线（backend/evals/agent/deepresearch/）取了中文 5 题确定性子集，被测系统逐题生成报告，产物 articles.jsonl（{id, prompt, article}）直接喂判分。判分逻辑按官方 score_calculator.py 移植，三个实现细节是读代码才发现的：

  • 权重匹配是模糊的：裁判回显的 criterion 文本要重新匹配回标准列表取权重，官方顺序是精确匹配 → 忽略大小写 → 子串包含，全都不中就用该维度平均权重兜底。裁判复述标准时改一个字，权重就走了兜底路径，和真实权重产生系统性偏差——影响多大没人披露，判分日志里也看不出来；
  • 裁判输出解析要宽容：markdown 代码栏、JSON 前后杂质都要容忍，四维齐备才算有效，我们的判分调用带 3 次重试，仍解析失败才记 judge output unparseable；
  • criterions 这个拼写错误要在序列化和匹配两端原样保留，任何一端「顺手修正」都会让数据对不上。

六、Harness 实战：跑 DeepResearch Bench 的工程现实

这部分是我们自己的账，全部来自搭评测线时的实测。

运行形态：每题一个独立 CLI 子进程驱动被测 SuperAgent 全链路（真实提示词、工具、子 Agent 派发），产物落 articles.jsonl，判分是独立的一步（--judge-model-id），跑题和打分可以分开重跑——判分方差和被测方差不能混在一个进程里。

单回合评测需要显式的交付契约。生产环境里深度研究任务可以委派后台子 Agent、等通知回合回来继续，但评测一题只跑一个回合——没有「后台任务完成」的回调。不把这一点讲清楚，Agent 会委派后台子 Agent 后直接结束回合，交付物变成「已转入后台」的状态说明。我们给每题附加一段评测模式说明：子 Agent 一律 run_in_background=false 前台等待；最终报告必须写在最后一条消息里（判分只读最后一条），或写入 /workspace/final-report.md 并在末条消息注明——缺一即视为未完成。

--eval-user 必须是真实账号。子 Agent 会话血缘按 user_id 落库，随手填个假用户名不会报权限错误，而是子 Agent 派发静默失败、主 Agent 孤军奋战——分数悄悄变低，日志里没有显式异常。这类「不报错的降级」是评测 harness 里最贵的 bug。

为什么是 DeepResearch Bench 而不是 BrowseComp：我们也建过 BrowseComp 评测线，后来整体移除了（完整复盘在仓库决策记录里）。BrowseComp 每题就是一次完整的深度研究 run，单位数据点成本远高于其他评测线；30 题基线在免费网关限流和外网可达性影响下动辄中断；而它的信号不再独占——端到端成功率由 Agentic RAG 线产出，SSE 链路稳定性由压测覆盖，报告质量这个能力条目由 DeepResearch Bench 子集线承担。评测体系的目标是每个能力条目有一个可辩护的数字，BrowseComp 对应不上任何独占条目。留下的教训比这条线本身值钱：选评测集和选技术栈一样要付维护成本，一条不稳定、贵、且信号可替代的评测线，比没有这条线更糟。

七、口径陷阱

  1. 相对分不是质量百分制。RACE 的 50 = 与专家参考持平；88 分的榜单数字意味着「打平一份 2025 年 4 月的 Gemini 快照」，不意味着报告有 88 分质量。
  2. judge 换版即断代。官方 judge 从 Gemini-2.5-Pro 换到 GPT-5.5，跨 judge 版本的分数对比必须在脚注里声明；自建 harness 至少要钉死 judge 模型并记录在结果 manifest 里。
  3. 位置偏差未被对冲。被测恒为 article_1，若你的系统在固定位置上系统性吃亏/沾光，RACE 分不出来。自建判分可以交换顺序跑两遍取均值——代价翻倍，我们还没做。
  4. 短答案基准与报告基准不可互证。BrowseComp 上 51.5% 的系统在 RACE 拿 48.88，两个数字测的是检索耐力和报告综合，量纲都不一样；选型时别拿短答案榜的排名推断报告能力。
  5. 题量决定置信区间。100 题的报告基准，单点分数的二项噪声已经不小；我们的 5 题子集只够冒烟，正式结论至少要全量 100 题。
  6. E.Cit 和 C.Acc 必须成对读。单独报一个「引用准确率 90%」可能是只引了 8 条撑得住的陈述；单独报「有效引用 111」可能混着两成撑不住的。

小结

DeepResearch Bench 把「报告好不好」这个 benchmark 里最主观的问题拆成了可操作的协议：内容质量交给 RACE——逐题自适应标准、双盲对比、相对分压制 judge 漂移；引用可信度交给 FACT——抽取、抓取、二值支持判定、两个成对阅读的指标。它给的不是分数而是尺子（全套开源判分脚本），这是它成为报告评测参照系的根本原因。

如果要带走一个观察：报告评测的可靠性不是来自更聪明的裁判，而是来自协议设计——权重不进 prompt、参考报告同场对比、引用与内容分离评、judge 一致率对标人类 IAA。我们把它整套搬进自己的 harness，改的只有入口和交付契约；协议本身一个字没动，这也是跑第三方基准应有的纪律。下一步的已知缺口同样清楚：位置偏差对冲、5 题子集扩到全量、判分方差的人工抽检校准。
